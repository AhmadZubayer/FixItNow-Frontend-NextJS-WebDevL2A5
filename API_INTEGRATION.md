# Frontend to Express API map

Source audit: 2026-11-07. These paths are confirmed from `../FixItNow-backend-server/src/app.ts` and its `src/modules/*/*.route.ts` files. Public category, service, technician list, and technician detail GETs returned HTTP 200. Selected protected and mutation routes were tested against the configured Prisma Postgres database as described below. Routes return `{ success, statusCode, message, data }` through `src/utils/sendResponse.ts`; errors return `{ success: false, message, errorDetails }`. Auth middleware accepts an `accessToken` cookie or Bearer token and checks the current database user and role.

| Frontend feature | Actual route and authorization | Request / relevant response | Source |
|---|---|---|---|
| Register/login/session | `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me` (auth), `POST /api/auth/refresh-token` | Register `{name,email,password,role}` (`CUSTOMER`/`TECHNICIAN`); login `{email,password}` returns access and refresh tokens; refresh `{refreshToken}` returns access token; `me` returns identity/role | `auth/auth.routes.ts`, `auth/auth.validation.ts`, `auth/auth.controller.ts` |
| Public categories | `GET /api/categories` | Category list | `category/category.route.ts` |
| Public services | `GET /api/services` | Optional `categoryId`, `location`, `minPrice`, `maxPrice`, `minRating`; no text search parameter | `service/service.route.ts`, `service/service.validation.ts` |
| Public technicians | `GET /api/technicians`, `GET /api/technicians/:id` | List optionally filters by `categoryId`, `location`, `minRating`; detail requires UUID | `technician/technician.route.ts`, `technician/technician.validation.ts` |
| Technician profile | `GET /api/technician/profile`, `PUT /api/technician/profile` (technician) | Owner-only profile read and `{bio?,skills,experienceYears?,location,profilePhoto?}` save | `technician/technician.route.ts`, `technician/technician.validation.ts` |
| Technician service | `POST /api/technician/services`, `PATCH /api/technician/services/:id` (technician) | Create `{title,description,price,durationMinutes,categoryId}`; owner-only partial edit including `isActive`; price is a positive decimal string | `service/service.route.ts`, `service/service.validation.ts` |
| Technician availability | `PUT /api/technician/availability`, `PATCH /api/technician/availability/:id/block` (technician) | Add `{slots:[{startAt,endAt}]}` ISO datetimes with offsets; block own future slot only when no active booking | `availability/availability.route.ts`, `availability/availability.validation.ts` |
| Customer booking | `POST /api/bookings`, `GET /api/bookings`, `GET /api/bookings/:id`, `PATCH /api/bookings/:id/cancel` (customer) | Create `{serviceId,availabilitySlotId}`; server chooses price and time, claims a future slot; customer reads only own bookings | `booking/booking.route.ts`, `booking/booking.validation.ts`, `booking/booking.service.ts` |
| Technician booking | `GET /api/technician/bookings`, `PATCH /api/technician/bookings/:id` (technician) | Update `{status}` among `ACCEPTED`, `DECLINED`, `IN_PROGRESS`, `COMPLETED`; service checks ownership and transitions | `booking/booking.route.ts`, `booking/booking.validation.ts` |
| Stripe Checkout/payment reads | `POST /api/payments/create`, `GET /api/payments`, `GET /api/payments/:id` (customer) | Create `{bookingId,provider?:"STRIPE"}` returns `{paymentId,checkoutUrl}`; accepted own booking only; reads are customer-owned | `payment/payment.route.ts`, `payment/payment.validation.ts`, `payment/payment.service.ts` |
| Stripe webhook and returns | `POST /api/payments/webhook`, `GET /api/payments/return/success`, `GET /api/payments/return/cancel` | Webhook raw body and signed event; newly created Checkout Sessions return to frontend `/payment/*` pages. Legacy backend text returns remain mounted | `payment/providers/stripe/stripe.route.ts`, `stripe.webhook.ts`, `stripe.controller.ts`, `stripe.provider.ts` |
| Review | `POST /api/reviews` (customer) | `{bookingId,rating,comment?}`; rating integer 1–5 | `review/review.route.ts`, `review/review.validation.ts` |
| Admin users/bookings | `GET /api/admin/users`, `PATCH /api/admin/users/:id`, `GET /api/admin/bookings` (admin) | Status update `{activeStatus:"ACTIVE"|"BLOCKED"}`; no dedicated KPI endpoint | `admin/admin.route.ts`, `admin/admin.validation.ts` |
| Admin categories | `GET /api/admin/categories`, `POST /api/admin/categories`, `PATCH /api/admin/categories/:id` (admin) | Create `{name,slug,description?}`; partial owner-independent admin edit of fields and `isActive` | `category/category.route.ts`, `category/category.validation.ts` |

The backend has no text query, so `app/services/page.tsx` applies the Zod-validated text search to the returned service and technician arrays. `lib/public-api.ts` uses Axios and the server-only `API_BASE_URL` override. A local booking test confirmed 201, occupied-slot 409, cancellation 200, and slot release. Technician profile read/save, service create/edit/pause, availability add/block, booking accept/repeat-conflict, and cross-role 403 checks passed against configured Prisma Postgres. Admin login/read routes returned 200; invalid category edit returned 400, valid edit 200, unauthenticated read 401, and self-block 409. Frontend routes under `app/api/technician/` and `app/api/admin/` forward HTTP-only session credentials to these role-protected Express routes. A real Stripe test-mode Checkout Session was created for an accepted booking; repeat initiation returned 409. Its actual Session URL pointed at the frontend return pages. That generated Session was later expired through Stripe's API; an invalid webhook signature returned 400, a locally signed expiration event referencing the actual Session returned 200 and persisted `CANCELLED`, and replay returned 200. The expiration event was signed and posted by the local test process, not delivered by Stripe's listener. A paid Checkout and live delivered webhook remain unverified. Review and browser-level feedback tests remain unverified. Backend edits are local-only and must never be pushed under this authorization.
