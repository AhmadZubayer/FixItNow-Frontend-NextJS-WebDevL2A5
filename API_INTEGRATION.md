# Frontend to Express API map

Source audit: 2026-11-07, updated 2026-11-08. These paths are confirmed from `../FixItNow-backend-server/src/app.ts` and its `src/modules/*/*.route.ts` files. Public category, service, technician list, and technician detail GETs returned HTTP 200. Selected protected and mutation routes were tested against the configured Prisma Postgres database as described below. Routes return `{ success, statusCode, message, data }` through `src/utils/sendResponse.ts`; errors return `{ success: false, message, errorDetails }`. Auth middleware accepts an `accessToken` cookie or Bearer token and checks the current database user and role. The table describes the locally edited backend; the current deployed backend is older. Its public categories route returned 200, but `GET /api/technician/profile` returned 404, so the backend deployment must be updated without pushing its Git repository before hosted role flows can pass.

The backend has no text query, so `app/services/page.tsx` applies the Zod-validated text search to the returned service and technician arrays. `lib/public-api.ts` uses Axios and the server-only `API_BASE_URL` override. Chrome verified valid/invalid public search, empty results, live technician detail, and a backend-outage error boundary. Booking browser tests created and cancelled one generated booking, created and declined another, confirmed disabled pending/error feedback, and left the generated service paused with no active future slots. A concurrent two-request test against one generated slot returned exactly 201 and 409; the winning booking was cancelled and the slot blocked afterward. Prior tests confirmed occupied-slot 409 and slot release. Technician profile read/save, service create/edit/pause, availability add/block, booking accept/decline/start/complete, repeated-transition conflicts, and cross-role 403 checks passed against configured Prisma Postgres. Admin login/read, valid/invalid/duplicate category creation/edit, search/pagination, ban/unban, and customer-role 403 checks passed through frontend or Express routes. Frontend routes under `app/api/technician/` and `app/api/admin/` forward HTTP-only session credentials to these role-protected Express routes. A real Stripe test-mode Checkout was completed by the user; the Stripe CLI listener forwarded a signed `checkout.session.completed` event to the isolated backend, which persisted payment `COMPLETED` and booking `PAID`. Chrome confirmed the success page, payment history, and booking history read those values from the backend. Two signed replays of the actual completed event returned 200 without changing persisted state. A separate generated Session was expired through Stripe's API; an invalid webhook signature returned 400, a locally signed expiration event returned 200 and persisted `CANCELLED`, and replay returned 200. After the paid booking reached `COMPLETED`, Chrome verified review invalid field, pending/API-error, successful 201 submission, and duplicate 409. The deployed webhook endpoint secret has not been verified. Backend edits are local-only and must never be pushed under this authorization.
