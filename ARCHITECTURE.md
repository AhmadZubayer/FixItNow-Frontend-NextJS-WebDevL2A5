# Architecture audit and implementation notes

Audited 2026-11-07. The frontend is an npm/`package-lock.json` Next.js 16.4.5 App Router project with React 19.3, Axios 1.21, Zod 4.6, and an installed shadcn `base-mira` preset using `mist` color tokens. It has root `app/`, `components/`, `lib/`, `hooks/`, and `validations/` directories, with no `src/`. The current `app/page.tsx` is the Create Next App starter. Preserve `components.json`, `app/globals.css`, and the installed `components/ui/` primitives. The reference audit is in `REFERENCE_STYLE.md`.

The sibling backend is Express 5.2 and Prisma 7.10. `src/app.ts` mounts public and role-restricted routes. Responses use `src/utils/sendResponse.ts` (`success`, `statusCode`, `message`, `data`); `src/middlewares/globalErrorHandler.ts` returns `success: false`, `message`, `errorDetails`. `src/middlewares/auth.ts` accepts an `accessToken` cookie or Bearer token, verifies the JWT, reloads the user, rejects blocked accounts, and checks required roles. Login currently returns access and refresh tokens in JSON. A secure frontend session design must avoid exposing long-lived refresh tokens to browser JavaScript and should handle logout and expiry deliberately. Next.js 16 route checks use `proxy.ts`, with Express authorization remaining authoritative.

`prisma/models/booking.prisma` stores slot, service, customer, immutable booking price, and status. `src/modules/booking/booking.service.ts` claims a future available slot inside a transaction and checks active bookings. `prisma/models/payment.prisma` stores provider transaction and refund references. `src/modules/payment/payment.service.ts` only creates Checkout for a customer-owned `ACCEPTED` booking, takes amount from the database, prevents a pending duplicate, and moves paid booking/payment state in a transaction. Stripe webhook verification and callback behavior are documented in `STRIPE_INTEGRATION.md`.

Known API gaps from route inspection: no technician profile read route under `/api/technician`, no availability read route under `/api/technician/availability`, no admin aggregate endpoint, and no category update route. Existing public technician and service reads may supply some of the needed data. The Stripe success/cancel returns are currently plain backend text, so frontend outcome routes need a backend redirect change or another verifiable return link. Proposed backend edits are not yet implemented.

Frontend API base URL, hosted deployment, and test accounts remain unverified. Do not assume local or hosted connectivity. All forms will use root `validations/*.validation.ts` (matching backend filename convention) with server-side validation retained. No backend files have been edited during this audit.
